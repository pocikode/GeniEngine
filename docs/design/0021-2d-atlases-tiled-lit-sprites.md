# 0021: Sprite atlases, Tiled maps and lit sprites

Milestone: After v0.1 (2D, following 0017) · Status: Done · Last updated: 2026-11-13

## Problem

0017 left three things open. **Atlases**: every sprite image is its own texture, so a
scene with a hero, coins and crates draws one batch per image, and artists must lay frames
out on a grid by hand. **Tiled**: levels are painted in the editor's tilemap inspector or
generated by a script; most 2D artists use Tiled (mapeditor.org) and expect to import its
maps. **Lit sprites**: sprites ignore the sun, ambient light and point lights, so a 2D game
at night, or sprites in a 3D world (billboard trees, signs), do not match the scene.

**Done** means: a `.gatlas` file lists images and the cooker packs them into one sprite
texture with named regions, which `SpriteComponent` uses by name; a Tiled JSON map
(`.tmj`) cooks into a scene with one tilemap per tile layer, colliders from a tile
property and objects from object layers; `SpriteComponent::lit` lights a sprite like a
flat surface facing its normal; Geni Plains uses an atlas for its hero, coins and crates
(fewer batches, same picture); tests cover each part.

## Approach

**Atlases.**
- Source `<name>.gatlas`: `{"format": "geni.atlas", "version": 1, "images": [paths
  relative to the file], "padding": 1}`. The cooker loads the images, packs them by height
  into shelves in the smallest power-of-two texture that fits (up to 4096), copies each
  image's border `padding` pixels outwards so filtering never reaches a neighbour, and cooks
  the result as a sprite texture (`TextureUsage::Sprite`). The atlas asset (type `atlas`)
  is JSON: the texture ID, its size, and each region's pixel rectangle under the image's
  file stem (`"hero"`).
- `SpriteComponent` gets `atlas` (asset ID) and `region` (name). With both set, the quad's
  UVs are the region's rectangle, and `columns`/`rows`/`frame` cut the region instead of
  the whole texture, so animation works unchanged. `ResolveAssets` loads the atlas (a small
  JSON, synchronously) and its texture (asynchronously, as now).

**Tiled maps.**
- The cooker reads `.tmj` (Tiled's JSON format; the XML `.tmx` is rejected with a message
  to export JSON): orthogonal maps, finite layers, CSV-free `data` arrays, tilesets embedded
  or in `.tsj` files, one tileset image each.
- Output: a scene asset (`scene:<path>`, the same as a cooked glTF scene) whose root holds
  one object per tile layer with a `TilemapComponent` (tile size 1 world unit, rows flipped
  because Tiled's Y points down, the tileset image as the texture with `columns`/`rows`
  from the tileset, the layer's index as the sprite layer). A tile with the boolean custom
  property `solid` lands in `solidTiles`; a layer with `collision: true` gets colliders.
  Object layers become empty objects named after the Tiled object (position at its bottom-
  left, in tiles), so a game finds spawn points with `FindObject`. Only the first tileset of
  a layer is used; flipped-tile bits are dropped (logged).

**Lit sprites.**
- `SpriteComponent::lit` (and `SpriteCommand::lit`, also for particles via
  `ParticleEmitterComponent::lit`) selects a lit variant of the sprite shader: the texel is
  lit by the sun (no shadows), ambient and the clustered point and spot lights, with the
  quad's normal (+Z of the object for flat sprites; towards the camera for billboards),
  using the same `geni.lighting` functions as meshes. Unlit stays the default (exact colours
  for pixel art). Batches split on lit as on blend.

Order of work: atlases (cooker, runtime, platformer); lit sprites; Tiled import; docs.

## Rejected

- **Runtime packing.** Packing at load costs time on every start and needs the source
  images in the package; the cooker already owns image processing.
- **TexturePacker / Aseprite formats.** Proprietary tools; a `.gatlas` list is enough, and
  Aseprite sheets work today as grid textures.
- **Normal-mapped sprites.** Needs a second texture per sprite; flat lighting first.
- **Infinite Tiled maps, isometric and hexagonal maps, image layers.** Not used by the
  sample; each is a small extension of the importer.
